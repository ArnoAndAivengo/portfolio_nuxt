Архитектура фронтенда CodeVega построена для предсказуемости, масштабируемости и удобства командной работы — особенно по мере роста приложения.

В основе лежит — **Feature-Sliced Design (FSD)**: модульная методология, которая задаёт строгие правила организации кода по слоям, слайсам и сегментам. 
Код делится по бизнес-смыслу, зависимости идут только в одну сторону, у каждого модуля есть публичный API. 
Это делает структуру проекта одинаково понятной и для нового разработчика, и для того, кто возвращается к коду через полгода.

## Как выглядит плохая архитектура

Чтобы понять архитектурный подход, принятый в CodeVega, сначала посмотрим на антипример — проект, который работает, но сопровождать его дорого.

- **Один файл стилей на 30 000+ строк.** Все стили лежат в `style.css`, архитектуры стилей нет, местами — inline-стили прямо в разметке.
- **Страница на тысячи строк.** В одном файле — запрос к API, store, разметка и стили.
- **Плоский каталог `components/`.** В нём вперемешку: `header`, `footer`, `modal`, `btn`, система оплаты, логика профиля.
- **API внутри компонентов.** Рядом с UI — сущности и бизнес-логика.
- **Библиотека на каждую мелочь.** Больше 20 зависимостей, часть дублируется, импортируются в каждый компонент, единой точки входа нет.
- **Нет линтеров и форматтеров.** В коде соседствуют табы и пробелы, единого стиля нет.
- **Нет TypeScript.** Проект без типизации.

Такой проект собирается и даже запускается. Но дальнейшее сопровождение превращается в постоянную трату времени: каждая новая фича это риск что-то сломать. 
Даже на уровне прототипа это замедляет команду.

## Feature-Sliced Design

Код лежит слоями, и зависимость идёт только вниз:

```
app → pages → widgets → features → entities → shared
```

- **app** — поднимает приложение: конфиг модулей, middleware, провайдеры.
- **pages** — маршруты Nuxt. Страница почти ничего не решает сама, она собирает блоки.
- **widgets** — крупные куски экрана: шапка, подвал, карточка статьи, редактор урока.
- **features** — одно действие пользователя: войти, открыть урок, отфильтровать список.
- **entities** — сущности предметной области: статья, курс, урок, пользовательская статистика.
- **shared** — то, у чего нет бизнес-имени: кнопка, API-клиент, токены вёрстки.

Виджет может собрать фичу. Фича может взять сущность. Сущность не импортирует виджет. Если правилу следуют, круговые зависимости неоткуда взять.

Карта слоёв и разрешённых импортов уже описана: каждый слайс — отдельный элемент, по умолчанию чужой слайс закрыт.

Правило линтера, которое это проверяет, сейчас выключено: на этапе активной разработки строгие границы мешают быстрым экспериментам. Направление зависимостей держится договорённостью и ревью.

Следующий шаг — включить проверку в сборку, когда структура стабилизируется и слайсы перестанут переезжать.

## Какие паттерны используются

1. **Слоистая архитектура (Layered Architecture).** Код делится на слои `app → pages → widgets → features → entities → shared`. Зависимости идут только вниз — это вариант классической layered architecture, адаптированный под фронтенд.
2. **Модульность через слайсы (Slices).** Внутри слоя — слайсы по бизнес-смыслу: `features/add-to-cart`, `entities/user`. Каждый слайс — мини-модуль с публичным API через `index.ts`.
3. **Публичный API (Barrel / Facade).** Каждый слайс экспортирует наружу только то, что нужно, через `index.ts`. Внутренние файлы не импортируются напрямую — это Facade-паттерн.
4. **Dependency Inversion на границах.** Слои не знают о конкретных реализациях нижележащих модулей — только об их публичных контрактах (типах, функциях).
5. **Композиция вместо наследования.** Вместо mixins и HOC — composables (Vue) и хуки. Логика собирается из маленьких функций.
6. **Adapter и DTO ↔ Domain Model.** Приведение данных из API к внутренней модели сущности. Адаптеры живут в `entities/*/api` или `entities/*/model`.
7. **Store (Pinia).** Единая точка состояния внутри слайса — в сегменте `model`.
8. **Discriminated Union и Type Guards.** Состояния через union с общим полем-дискриминатором, сужение типов через функции-предикаты.
9. **Schema-first (Zod).** Тип выводится из схемы валидации и не пишется руками. Закрывает границы API, localStorage, URL.

## Как устроена правильная архитектура

- **Структура разбита по бизнес-сущностям.** Фича — отдельно, типы — отдельно, API и бизнес-логика — отдельно. У каждого файла есть своё логическое место.
- **Стили структурированы и изолированы.** Разбиты по файлам и слоям, конфликты имён исключены, правки в одном месте не ломают другое.
- **Файлы разложены по структурам.** `shared` содержит `ui`, `types`, `stores` и т.д. — у всего есть своё место.
- **Нет глобальной папки `components/`.** Компоненты живут в `entities`, `features`, `shared`, `layouts` — там, где они принадлежат по смыслу. Внутри слайсов при этом есть свои `ui/`.
- **API — на своём месте.** Общий клиент — в `shared/api`, запросы сущности — в `entities/*/api`, состояние — в `model` соответствующего слайса.
- **Единая точка импорта библиотек.** Нет дублирующих вызовов, обёртки и реэкспорты собраны в одном месте.
- **Правила зафиксированы.** Для Nuxt, Vue, Composition API, TypeScript, импортов и FSD есть явные правила — в конфигах линтеров и в документации проекта.
- **TypeScript как основной язык.** Даёт ускорение разработки, безопасный рефакторинг и самодокументируемость кода.

Такой проект легко масштабируется: новые фичи вносятся быстрее, а онбординг команды проходит проще — при условии, что разработчики знакомы с FSD. 
Новичку достаточно один раз понять структуру.

## Зачем разбивать приложение

Декомпозиция нужна, чтобы изменение имело границу.

- Фичу можно выключить флагом и не вычищать её из десятка страниц.
- Часть задачи можно отдать другому человеку: он работает с отдельным слайсом.
- Ошибка в квизе или уроке не обязана ломать шапку.

Без этой границы любая оптимизация начинается с поиска по всему проекту. Сначала ищешь, кто вообще импортирует файл. 
Потом боишься его трогать. Потом копируешь рядом второй такой же и это опять время.

## Зачем перегружать проект библиотеками

Библиотека — это зависимость, которую придётся обновлять и тащить в бандл. Пакет оправдан если закрывает задачу продукта.

На CodeVega библиотеки оправданы. Пакеты находятся внутри своих фичь. Например, Главная страница за них не отвечает и точно знаешь, что эта страница не сломается.

Правило простое. Если пакет закрывает задачу и продукт без нее не работает, то пакет попадает в сборку.

## Что из этого следует

Архитектура нужна в любом проекте — и в лендинге на одну страницу, и в большой платформе. 
Разница только в масштабе: где-то достаточно аккуратной структуры папок, где-то — FSD, реестра модулей и правил на импорты. 
Но принцип один: код должен иметь границы, а изменение — не расползаться по всему репозиторию.

Архитектура CodeVega строилась на будущее. Продукт будет расти — появятся новые модули, роли, сценарии. 
Задача архитектуры в том, чтобы каждая новая фича не требовала переписать половину проекта. 
Поэтому слои, границы и правила появились раньше, чем в них возникла острая нужда.

Это и есть профессиональный подход: заложить архитектуру заранее и строить уже на готовом прочном фундаменте.
