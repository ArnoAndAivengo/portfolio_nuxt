Сегодня расскажу, как я работаю с кодом через **локальную LLM**, без облачных API.

- Почему локально.
- Как поднял **Ollama** и **Qwen2.5-Coder 32B** на сервере.
- Как «обучаю» модель правилами и как крутится **Continue** в VS Code.

## Зачем локальная модель

Облачные ассистенты удобны (Cursor, Claude) — всё настроено, только плати. Но код при этом уезжает наружу. Мои правила простые:

1. **Код не должен уезжать наружу по умолчанию.** Клиентский и внутренний контур — не материал для чужого датасета.
2. **Контроль моделей.** Модель с правилами по нашему стеку выдаёт меньше шума.
3. **Интерес разобраться.** Хотел сам поковыряться в LLM.

## Железо: Сервер под локальный AI

| Параметр | Значение |
| --- | --- |
| ОС | Ubuntu Server 24.04 |
| ОЗУ | 128 ГБ |
| GPU | NVIDIA RTX 5090, 32 ГБ VRAM |
| Runtime | [Ollama](https://ollama.com) |
| Основная модель | `qwen2.5-coder:32b` |

128 ГБ RAM — запас на длинный контекст, offload слоёв и параллельные Docker-проекты. 32 ГБ VRAM на 5090 — комфорт для **32B в Q4**: веса помещаются, остаётся место под контекст. FP16 на 32B сюда уже не влезает.

Ориентиры по размеру:

| Модель | Зачем | Ощущение на 5090 |
| --- | --- | --- |
| `qwen2.5-coder:32b` | чат, ревью, рефакторинг | «умный», секунды–десятки секунд на ответ |
| `qwen2.5-coder:7b` | короткие вопросы | заметно быстрее 32B |
| `qwen2.5-coder:1.5b` | tab autocomplete | задержка важнее глубины |

Схема простая:

```
VS Code (рабочая машина) ──Continue──► Ollama :11434 (Сервер)
                                              │
                                              ▼
                                    qwen2.5-coder:32b  (чат / агент)
                                    qwen2.5-coder:7b   (лёгкие задачи)
                                    qwen2.5-coder:1.5b (autocomplete)
```

## Подъём Ollama на Ubuntu 24.04

### Установка Ollama

```
curl -fsSL https://ollama.com/install.sh | sh
systemctl status ollama
ollama --version
```

Сервис слушает `127.0.0.1:11434` по умолчанию. Для доступа с другой машины в LAN:

```
# /etc/systemd/system/ollama.service.d/override.conf
[Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"
Environment="OLLAMA_KEEP_ALIVE=30m"
```

```
sudo systemctl daemon-reload
sudo systemctl restart ollama
```

`OLLAMA_KEEP_ALIVE=30m` — чтобы после короткого перерыва не ждать снова загрузку 32B в VRAM. Для «всегда в памяти» ставят `-1` (карта занята).

**Подводный камень:** открытый `0.0.0.0` без firewall/VPN — любой в сети может дергать модель. Практичнее VPN или SSH-туннель:

```
ssh -N -L 11434:127.0.0.1:11434 user@Сервер
```

Тогда в Continue `apiBase` остаётся `http://localhost:11434`.

### Модели

```
ollama pull qwen2.5-coder:32b
ollama pull qwen2.5-coder:7b
ollama pull qwen2.5-coder:1.5b

ollama list
ollama run qwen2.5-coder:32b "Напиши функцию debounce на TypeScript"
```

- **32B** — чат, ревью, рефакторинг, «разбери этот дифф».
- **7B** — быстрее на коротких вопросах.
- **1.5B** — для **tab autocomplete**: там важна задержка, а не глубина рассуждения.

Проверка, что инференс идёт на GPU:

```
# во время генерации
nvidia-smi
# процесс ollama / runner ест VRAM, utilization > 0
```

Если VRAM почти пустая, а CPU в потолок — модель не на карте. Смотреть логи `journalctl -u ollama -f` и версию драйвера.

## Подводные камни, на которые наступил

| Боль | Что происходит | Как жить |
| --- | --- | --- |
| **Контекст vs VRAM** | 32B Q4 влезает, длинный контекст раздувает KV-cache → OOM | Резать `num_ctx`, не тащить весь репозиторий в один промпт |
| **«Обучение» ≠ дообучение** | Кажется, что модель «запомнила» проект после чата | Веса от диалога не меняются. Память — в правилах Continue |
| **Одна модель на всё** | 32B на каждый Tab — медленно | Роли: 32B чат, 1.5B autocomplete |
| **Keep-alive и «холодный старт»** | Первая генерация после простоя грузит веса заново | `OLLAMA_KEEP_ALIVE` (`30m` / `-1`) |
| **Сеть и Continue** | `apiBase` на localhost, Ollama на другой машине → connection refused | Туннель или LAN + firewall |
| **Драйвер 50xx** | Старый драйвер / mismatch CUDA | Сначала `nvidia-smi`, потом модели |
| **Русский + код** | Код ок, формулировки на русском «плывут» | Жёсткий `systemMessage` + короткие правила |
| **Галлюцинации API** | Выдуманные методы Nuxt/Vue | Правила стека + ревью глазами |

## Мини-история: как правило победило галлюцинацию

До `instructions.md` модель регулярно предлагала Options API и `this.$router` в свежем Nuxt 3. После двух строк в правилах:

> Только Composition API и `<script setup>`. Options API и `any` запрещены. Слои — FSD.

Те же промпты стали выдавать `composables/` и `ref` без споров. Веса модели не менялись — изменился **вход**. Это и есть ежедневное «обучение» в моём смысле.

## Как «ведётся обучение» модели

Слово «обучение» легко перепутать с fine-tuning. Разложу по слоям.

### 1. Инференс (то, чем пользуюсь каждый день)

Модель уже обучена авторами Qwen. Ollama только **запускает** её: токены на вход → токены на выход. Чаты в Continue веса не обновляют. Иначе кажется, что «я её уже научил нашему FSD», а через день она снова предлагает Options API.

### 2. Обучение поведением (то, что реально работает)

Чтобы модель вела себя как ассистент по Vue/Nuxt:

- **system message** — роль и язык ответа;
- **project rules / `instructions.md`** — что можно и что нельзя;
- **custom commands** — сценарии («рефакторинг», «создай composable»).

Это не fine-tuning. Каждый запрос = правила + выделенный код + вопрос. Чем короче правила, тем меньше модель фантазирует.

### 3. Настоящее дообучение (редко, и пока не основной путь)

Если понадобится узкая специализация:

1. собрать датасет;
2. LoRA / QLoRA поверх базы;
3. прогнать обучение на GPU;
4. подключить адаптер.

Для ежедневного рефакторинга **правил Continue + сильной базовой модели достаточно**.

Практический цикл:

```
написал правило в instructions.md
        ↓
проверил на 2–3 реальных задачах в Continue
        ↓
ужесточил формулировку / убрал шум
        ↓
зафиксировал в репозитории (.continue/)
```

Модель не меняется — меняется обвязка, и её можно версионировать в git.

## Continue в VS Code: правила и настройки

Continue — мост между редактором и Ollama. В репозитории лежит `.continue/`: конфиг моделей и инструкции под стек.

### Модели в config.json

```
{
  "models": [
    {
      "title": "Qwen Coder 32B",
      "provider": "ollama",
      "model": "qwen2.5-coder:32b",
      "apiBase": "http://localhost:11434"
    },
    {
      "title": "Qwen Coder 7B",
      "provider": "ollama",
      "model": "qwen2.5-coder:7b",
      "apiBase": "http://localhost:11434"
    }
  ],
  "tabAutocompleteModel": {
    "title": "Qwen Coder 1.5B (Fast)",
    "provider": "ollama",
    "model": "qwen2.5-coder:1.5b",
    "apiBase": "http://localhost:11434"
  },
  "systemMessage": "Ты - AI-помощник для разработки на Vue 3 + Nuxt 3 с TypeScript. Отвечай на русском языке. Следуй правилам: FSD архитектура, Composition API, TypeScript strict без any, отступы 4 пробела.",
  "customCommands": [
    {
      "name": "Создать компонент",
      "prompt": "Создай Vue 3 компонент с Composition API и TypeScript, используя FSD структуру. Отступы 4 пробела. Комментарии на русском."
    },
    {
      "name": "Создать composable",
      "prompt": "Создай composable для Nuxt 3 с TypeScript. Используй правильную реактивность. Отступы 4 пробела."
    },
    {
      "name": "Рефакторинг",
      "prompt": "Отрефактори этот код: используй Composition API, добавь типы, убери any, оптимизируй реактивность. FSD структура. Ответ на русском."
    }
  ]
}
```

`apiBase: http://localhost:11434` работает и локально, и через SSH-туннель.

> Новые версии Continue чаще живут в `config.yaml`. У нас пока `config.json` — суть та же: разные модели на разные роли.

### Правила в instructions.md

То, что модель должна видеть **каждый** раз:

- FSD: куда класть фичи / виджеты / сущности / utils;
- Vue 3: Composition API, `<script setup>`, `ref` / `reactive`, composables;
- TypeScript strict, без `any`;
- Nuxt 3: `useFetch` / `useAsyncData`, `definePageMeta`, `useRuntimeConfig`;
- форматирование: 4 пробела, порядок блоков в `.vue`.

### Как пользоваться в ежедневной работе

| Сценарий | Как |
| --- | --- |
| Ревью куска | Выделить код → Continue chat → «найди риски и упрощения» |
| Рефакторинг | Команда **Рефакторинг** |
| Новый UI-блок | **Создать компонент** + слой FSD |
| Автодополнение | Tab на 1.5B |
| Контекст | `@filename` / `@codebase` по делу; не скармливать всё подряд |

Модель предлагает — **я принимаю или нет**. Локальный LLM не снимает ответственность за дифф в merge request.

Для учеников на платформе мы боремся с подменой мышления. Для себя тот же принцип: ассистент — ускоритель, не автор решений.

## Где было сложнее всего

| Область | В чём боль |
| --- | --- |
| Драйверы RTX 5090 | Без рабочего `nvidia-smi` весь стек бессмысленен |
| Баланс VRAM / контекст | 32B влезает, жадность к контексту — нет |
| Ожидания от «обучения» | Правила и промпты ≠ fine-tune |
| Сеть Continue ↔ Ollama | localhost vs Сервер, туннель, firewall |
| Дисциплина ролей моделей | Хочется всё на 32B — страдает autocomplete |
| Качество ответа | Нужен человеческий ревью и жёсткий `instructions.md` |

## Будущие планы

Текущая связка уже даёт пользу. Дальше — от «ИИ в IDE» к системному контуру.

### 1. Автономные агенты для рутины

Черновики миграций, changelog, простые рефакторинги — с обязательной проверкой человеком перед merge.

### 2. ИИ в CI/CD

Проверка диффа на антипаттерны стека, подсказки к упавшим тестам, черновик описания MR.

### 3. Мониторинг и сравнение моделей

Нужны простые замеры: latency, доля принятых предложений Tab, число отклонённых чатов.

### 4. Документация

- как ставить задачу модели и как проверять ответ;
- шаблоны промптов;
- правила работы с чувствительным контекстом;
- актуализация `devDocs` и `.continue/`.

### 5. Новые модели

Qwen2.5-Coder 32B — сильная база. Дальше — эксперименты с новыми coder-моделями **на том же железе**, без ломания рабочего контура.

## Что в итоге

- Код и внутренний контекст остаются локально.
- Модель, параметры и правила развиваются своими силами.
- Черновики, рефакторинг, ревью — быстрее.
- `.continue/config.json` и `instructions.md` в git — поведение ассистента воспроизводимо.
- Меньше зависимости от API-лимитов, сбоев и скачков цен облака.

Локальный ИИ не заменяет разработчика инженера и не отменяет code review. Он только ускоряет ежедневную рутину.
